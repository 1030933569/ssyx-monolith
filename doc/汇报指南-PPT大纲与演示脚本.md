## 第 6 页：核心流程——用户登录

**页面内容（建议画流程图）：**

```
小程序 wx.login() 拿到 code
        ↓
调后端 /api/user/weixin/wxLogin/{code}
        ↓
后端用 code 调微信 jscode2session 拿到 openid
        ↓
openid 查用户表（没有就新建）
        ↓
生成 JWT token + 缓存登录态到 Redis
        ↓
返回 token 给小程序（后续每次请求带上）
```

**你说：**
> 用户登录是整个系统的入口。小程序调用 wx.login 拿到一个临时 code，把 code 传给后端，后端再拿这个 code 去微信服务器换取用户的 openid。有了 openid 就能识别用户身份，然后生成一个 JWT token 返回给小程序。之后小程序每次请求都在请求头里带上这个 token，后端通过拦截器解析 token 就知道是哪个用户在操作。

---

## 第 7 页：核心流程——购物车（Redis 实现）

**页面内容：**
- 存储结构：Redis Hash
  - key：`user:{userId}:cart`
  - field：`skuId`（商品ID）
  - value：`CartInfo`（商品名、数量、是否勾选）
- 过期时间：7 天
- 为什么用 Redis 而不是 MySQL：购物车读写极其频繁，Redis 内存操作比数据库快几十倍

**你说：**
> 购物车是一个读写非常频繁的功能，用户可能反复加减商品、勾选取消。如果每次都读写数据库，性能会很差。所以我把购物车数据存在 Redis 里，用 Hash 结构，每个用户一个 key，里面每个商品是一个 field。这样加购、改数量、勾选这些操作都是毫秒级完成的。设了 7 天过期，避免 Redis 内存无限增长。

---

## 第 8 页：核心流程——下单（重点页，多讲）

**页面内容（建议画流程图）：**

```
用户点击"提交订单"
      ↓
① 防重校验：Redis + Lua 脚本（同一个订单号只能提交一次）
      ↓
② 锁库存：Redisson 分布式锁 + MySQL 扣减（防超卖）
      ↓
③ 落库：事务写入 order_info + order_item 表
      ↓
④ 异步消息：通知清除购物车已下单商品
```

**你说：**
> 下单是整个系统最核心的环节，我重点讲一下。首先是防重——用户可能因为网络卡顿连续点了两次提交，系统用 Redis + Lua 脚本保证同一个订单号只能成功提交一次。然后是锁库存——多个用户同时买同一个商品时，用 Redisson 分布式锁保证库存扣减不会出错，防止超卖。校验通过后，在一个数据库事务里写入订单主表和订单明细表。最后通过异步消息把购物车里已下单的商品清掉。

---

## 第 9 页：核心流程——支付与异步处理

**页面内容：**

```
小程序调起微信支付
      ↓
后端调微信统一下单接口，返回支付参数
      ↓
用户完成支付
      ↓
后端轮询/回调确认支付成功
      ↓
异步处理：更新订单状态 → 扣减 MySQL 库存 → 清购物车
```

**你说：**
> 支付对接的是微信支付。后端调用微信统一下单接口拿到支付参数，小程序用这些参数调起支付界面。支付成功后，系统会异步处理三件事：把订单状态从"未支付"改成"待发货"，扣减 MySQL 里的实际库存，以及清除购物车中已下单的商品。这里用异步消息而不是同步处理，是为了让支付接口响应更快，用户体验更好。

---

## 第 10 页：总结与展望

**页面内容：**
- 已实现：用户登录、商品浏览、购物车、下单、支付、提货点管理
- 技术亮点：Redis 购物车、分布式锁防超卖、Lua 防重、异步消息解耦
- 未来可扩展：接入 ElasticSearch 做全文搜索、用 RabbitMQ 替换 Redis MQ、拆分为微服务架构

**你说：**
> 总结一下，这个系统实现了社区团购的核心业务闭环：从用户登录、浏览商品、加购物车，到下单支付、异步处理。技术上重点解决了三个问题：用 Redis 提升购物车性能，用分布式锁防止库存超卖，用 Lua 脚本防止重复下单。未来如果要继续优化，可以接入 ElasticSearch 做商品全文搜索，用 RabbitMQ 替换目前的 Redis 消息队列，以及把单体拆分成微服务架构。以上就是我的汇报，谢谢各位老师。

# 三、代码走查路线（老师要看代码时用）

> 如果老师说"打开代码看看"，按下面的顺序展示，每个点讲 1-2 句话就够。

---

## 路线 1：登录鉴权（3 个文件）

**第 1 站：JWT 工具类**
- 文件：`common/common-util/src/main/java/cn/itedus/ssyx/common/utils/JwtHelper.java`
- 讲：这个类负责生成和解析 JWT token，createToken 方法把 userId 加密进 token，parseToken 方法从 token 里解出 userId。

**第 2 站：登录拦截器**
- 文件：`common/service-util/src/main/java/cn/itedus/ssyx/common/auth/UserLoginInterceptor.java`
- 讲：每次请求进来，拦截器从请求头取出 token，调用 JwtHelper 解析出 userId，存到 ThreadLocal 里，业务代码就能直接拿到当前用户。

**第 3 站：拦截器配置**
- 文件：`common/service-util/src/main/java/cn/itedus/ssyx/common/auth/LoginMvcConfigurerAdapter.java`
- 讲：这里配置了哪些路径需要拦截——所有 /api/ 开头的请求都要验证 token，但登录接口 /api/user/weixin/wxLogin 是放行的。

---

## 路线 2：购物车（1 个核心文件）

**文件：** `service/service-cart/src/main/java/cn/itedus/ssyx/cart/service/impl/CartInfoServiceImpl.java`

- `addToCart()`：加购物车，往 Redis Hash 里写入商品信息
- `cartList()`：获取购物车列表，从 Redis 读取并组装数据
- `checkCart()`：勾选/取消勾选商品
- `deleteCart()`：删除购物车中的商品
- 讲：所有购物车操作都是直接读写 Redis，没有走数据库，所以响应速度很快。

---

## 路线 3：下单（最核心，2 个文件）

**第 1 站：订单服务**
- 文件：`service/service-order/src/main/java/cn/itedus/ssyx/order/service/impl/OrderInfoServiceImpl.java`
- 重点方法：
  - `confirmOrder()`：生成防重订单号，写入 Redis
  - `submitOrder()`：Lua 脚本防重校验 → 调锁库存 → 事务落库
- 讲：submitOrder 是最关键的方法。先用 Redis + Lua 保证订单号只能用一次，再调商品服务锁库存，最后在事务里写入订单表。

**第 2 站：锁库存**
- 文件：`service/service-product/src/main/java/cn/itedus/ssyx/product/service/impl/SkuInfoServiceImpl.java`
- 重点方法：`checkAndLock()`
- 讲：这个方法用 Redisson 分布式锁锁住每个商品的库存，然后检查库存够不够，够的话就扣减。用分布式锁是为了防止多个用户同时买导致超卖。

# 四、追问应对手册（老师可能问的问题 + 回答模板）

> 按出现概率排序，背前 10 个基本够用。

---

## Q1：为什么选 Spring Boot 而不是 SSM？

> Spring Boot 是在 SSM 基础上的进一步封装，提供了自动配置和快速启动能力，不需要手动写大量 XML 配置。目前企业开发基本都用 Spring Boot，SSM 已经比较少见了。本质上 Spring Boot 内部还是用的 Spring MVC + MyBatis，只是开发效率更高。

---

## Q2：为什么购物车用 Redis 不用 MySQL？

> 购物车是高频读写场景，用户可能频繁加减商品、勾选取消。Redis 是内存数据库，读写速度比 MySQL 快几十倍。而且购物车数据是临时性的，不需要持久化保存，设置 7 天过期就行。如果用 MySQL，每次操作都要走磁盘 IO，在高并发下会成为性能瓶颈。

---

## Q3：JWT 是什么？为什么用它？

> JWT 全称 JSON Web Token，是一种轻量级的身份认证方案。用户登录后，服务端生成一个加密的 token 返回给客户端，之后每次请求客户端都带上这个 token，服务端解析就能知道是谁。好处是"无状态"——服务端不需要存 session，适合分布式部署和小程序这种前后端分离的场景。

---

## Q4：什么是分布式锁？为什么下单要加锁？

> 分布式锁就是在多个请求同时操作同一个资源时，保证同一时刻只有一个请求能执行关键操作。比如商品库存只剩 1 件，两个用户同时下单，如果不加锁，两个请求都读到库存是 1，都扣减成功，就超卖了。加了 Redisson 分布式锁后，同一时刻只有一个请求能扣库存，另一个要等前一个完成才能执行。

---

## Q5：Lua 脚本防重是怎么实现的？

> 提交订单前，系统会生成一个唯一的订单号存到 Redis 里。提交时用 Lua 脚本做"读取并删除"的原子操作——如果 Redis 里有这个订单号就删掉并放行，如果没有说明已经被用过了，直接拒绝。Lua 脚本在 Redis 里是原子执行的，不会出现并发问题。

---

## Q6：为什么用异步消息？不能同步处理吗？

> 可以同步，但体验不好。比如下单成功后要清购物车、支付成功后要扣库存和更新状态，这些操作如果都同步做，用户要等很久才能看到结果。用异步消息把这些"不紧急但必须做"的事情放到后台处理，接口可以更快返回，用户体验更好。而且异步还能起到"削峰"的作用——高并发时不会把数据库压垮。

---

## Q7：为什么搜索没用 ElasticSearch？

> ElasticSearch 确实更适合做全文搜索，但它部署和运维成本比较高，对服务器资源要求也大。作为毕设项目，优先保证系统能跑通、易部署，所以用 MySQL 条件查询 + Redis 热度榜来实现搜索功能。代码结构上已经做了模块化设计，将来要升级成 ES 只需要替换搜索模块的实现，不影响其他业务。
